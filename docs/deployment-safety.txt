როგორ მუშაობს დაცვა

ახალ პროცესს საკუთარი, პროცესის სიცოცხლის განმავლობაში უცვლელი writer token
აქვს. 019 მიგრაცია ცალკე, საჯარო API-დან მიუწვდომელ masterboy_deploy სქემაში
ინახავს მხოლოდ მიმდინარე მწერლის მეტამონაცემს. მომხმარებლის, გადახდისა და
ვადების ცხრილების სტრუქტურა და არსებული ჩანაწერები არ იცვლება. მათზე ემატება
ჩაწერის დამცავი trigger-ები.

ახალი პროცესის უფლება, კოლექციების ჩატვირთვა და გაშვების აუცილებელი შენახვა
ერთ ტრანზაქციაში სრულდება. არსებული პროცესის ტრანზაქციები ჯერ სრულდება,
შემდეგ ახალი პროცესი ბაზიდან ახალ მდგომარეობას იტვირთავს. მისი წარმატებული
გაშვების შემდეგ SQL დონეზე ძველი token-ით ნებისმიერი INSERT/UPDATE/DELETE/
TRUNCATE უარყოფილია. ძველი pool-ის ხელახლა დაკავშირება token-ს არ ცვლის.

ჩაწერის ტრანზაქციები ჯერ writer-control-ის FOR SHARE ბლოკირებას იღებს და მხოლოდ
შემდეგ ბიზნესჩანაწერების ბლოკირებას. ახალი პროცესის დაწყება FOR UPDATE-ს იყენებს.
ასე ძველი გადახდის ტრანზაქციის კომიტსა და ახალი პროცესის ჩატვირთვას ერთი
თანმიმდევრობა აქვს. token ყველა ტრანზაქციაში SET LOCAL-ით გადაეცემა, ამიტომ
არ არის დამოკიდებული pool-ის ერთი კონკრეტული სესიის შენარჩუნებაზე.

თუ კონფიგურაციის წაკითხვა, ჰიდრატაცია ან HTTP პორტზე გახსნა ვერ დასრულდა,
მთელი საწყისი ტრანზაქცია ბრუნდება უკან. ძველი token და არსებული ვადები რჩება.
HTTP სერვერი ჩართული მზადყოფნის პასუხს მხოლოდ კომიტის შემდეგ გასცემს.
HTTP callbacks არ მემკვიდრეობს ჰიდრატაციის AsyncLocalStorage-ის კავშირს.

ცვლილების წარმატებული HTTP პასუხი საჭირო შენახვის დასრულებამდე არ იგზავნება.
დაკარგული writer-ის ან შენახვის ჩავარდნისას ბრუნდება რეალური 503 და Retry-After,
წარმატებული შედეგის სიმულაციის გარეშე. ბანკის უკვე ტრანზაქციულ callback/status
გზებზე დამატებითი სრული snapshot არ იწერება.

SIGTERM/SIGINT აჩერებს ახალი მუტაციების მიღებასა და პერიოდული reconciliation-ის
ახალ გაშვებებს, ელოდება მიმდინარე HTTP-ს, ბანკის მიმდინარე reconciliation-სა
და შენახვის რიგს, შემდეგ ხურავს pool-ს. 25-წამიანი ავარიული ზღვარი რჩება Render-ის
სტანდარტულ 30-წამიან იძულებით გათიშვამდე. მხოლოდ უკვე დასრულებული შენახვის
შედეგი ითვლება HTTP-ით დადასტურებულად. შეწყვეტილი BOG ოპერაციები არსებულ
დურაბელურ PENDING ჩანაწერსა და reconciliation-ს ეყრდნობა.

ეს პროცედურა ჯერ არ შესრულებულა. ჩვეულებრივი, აქტიური ტრაფიკის ფონზე პირველი
გაერთიანება/ავტოდეპლოი დაუშვებელია, რადგან ძველი 713f862 ვერსია პასუხს შენახვის
დასრულებამდე აგზავნის და ახალი მექანიზმის შესახებ არაფერი იცის.

   Git bundle მომხმარებლებისა და შესყიდვების მონაცემთა ბაზის ასლი არ არის.

შემდგომი დეპლოი და დაბრუნება

დადასტურდება აუცილებელი კომიტის გარეშე. უკვე შენახული 30/180-დღიანი ვადები
აბსოლუტური თარიღებით გაგრძელდება.

დაცვა ჩართული დარჩეს. დაბრუნების სამიზნე უნდა იყოს შემოწმებული ვერსია,
რომელიც ამავე დაცვას იყენებს და იმავე writer-control-ით თავიდან იტვირთება.
